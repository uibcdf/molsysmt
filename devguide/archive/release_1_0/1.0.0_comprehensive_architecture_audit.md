# MolSysMT 1.0.0 Comprehensive Architecture Audit

> **Archived audit:** Conclusions and status labels apply to the audit context,
> not automatically to the current repository.

## Introduction

This document provides a detailed, unvarnished, and deep-dive technical audit of the MolSysMT codebase. The audit was conducted during the final stages of the "Phase 3: Great Cleanup" stabilization sprint (March 2026) and finalized during the "Documentation & Excellence Pass" (May 2026), targeting the 1.0.0 release.

The purpose of this audit is not to list failing tests, but to evaluate the **structural integrity, software engineering practices, performance infrastructure, and architectural cohesion** of MolSysMT as a framework.

---

## 1. The Core Engines: Strengths and Weaknesses

### 1.1 The High-Performance Engine (`molsysmt.lib` & Numba JIT)
**Diagnosis: Brilliant and Cutting-Edge.**

MolSysMT relies heavily on Numba to achieve C/Fortran-level execution speeds for computationally expensive topological and PBC (Periodic Boundary Conditions) operations. However, rather than applying a simple `@nb.njit` decorator—which in a library of this size would cause catastrophic compile-time storms—the architecture employs a custom **lazy compilation system** (`lazy_njit` in `_private/jit.py`).

*   **How it works**: The system scans the Abstract Syntax Tree (AST) of the function (`func.__code__.co_names`) to identify internal dependencies and pre-compiles them in the correct topological order. This prevents recursive locking.
*   **Integration**: It ties perfectly into `smonitor`, emitting a single `NumbaJitWarning` when compilation is triggered, offering complete transparency to the user.
*   **Technical Debt / Friction Point**: Numba requires strict typing (e.g., `nb.float64[:,:]`). MolSysMT trusts that upstream parsers (like MDTraj) provide the exact expected data type. If an external library suddenly returns `float32` (as MDTraj often does with `.dcd` boxes) or integers instead of floats, the JIT dispatcher will crash with a `TypeError`.
*   **1.0.0 Recommendation**: Ensure all internal calls to `msmlib` strictly cast inputs (e.g., `.astype(np.float64)`) immediately before passing them to the JIT layer to insulate the core from third-party type noise.

### 1.2 The Dimensional Bridge (`pyunitwizard`)
**Diagnosis: Mathematically Solid, API Sensitive.**

MolSysMT correctly isolates the performance penalty of unit handling from its mathematical core.
*   **The Pattern**: Data is ingested with units -> `puw.get_value` strips the unit -> Raw NumPy array is passed to `molsysmt.lib` -> Result is re-wrapped with `puw.quantity`. This is the safest and most performant pattern possible.
*   **Technical Debt / Friction Point**: The framework is highly sensitive to changes in the `pyunitwizard` API. During the audit, we noticed that operations like `puw.concatenate` vs `puw.utils.numpy.concatenate`, or the handling of empty arrays (`len(box) == 0`), could break native constructors if not carefully guarded. 
*   **1.0.0 Recommendation**: Continue centralizing `pyunitwizard` wrapper functions within MolSysMT (like the newly implemented `_puw_concatenate` in `Structures`) rather than calling external `puw` utility functions directly in business logic.

## 2. The Digestion System: A Masterpiece of Flow Control

The "Golden Quartet" of `smonitor`, `argdigest`, `depdigest`, and `pyunitwizard` forms the absolute backbone of MolSysMT's user-facing API. 

### 2.1 Argument Digestion (`@arg_digest`)
**Diagnosis: The Structural Pillar.**
Deployed across **~7,690 functions**, this decorator is the reason MolSysMT's codebase isn't choked with tens of thousands of lines of `if isinstance(...)` boilerplate. It ensures that inputs (`item`, `selection`, `structure_indices`) are standardized before the function logic begins. The internal propagation of `skip_digestion=True` is an excellent design pattern that prevents recursive performance penalties during deep stack calls.

*   **Friction Point**: Rigidity. `argdigest` assumes a "form" (forma) is typically a complex instantiated object or a file path. When introducing pure data-structure forms like `molsysmt.MolecularMechanicsDict` (a standard Python `dict`), the ingestion system struggles to classify it without hardcoded bypasses.

### 2.2 Dependency Shielding (`@dep_digest`)
**Diagnosis: Highly Robust.**
There are **74 active deployments** of `@dep_digest`. This operates as a dependency firewall. It protects the code paths associated with heavy external libraries (`openmm`, `mdtraj`, `Bio`, `nglview`), guaranteeing that `import molsysmt` executes in milliseconds. If a user only wants to use NGLView, they do not suffer import penalties or crashes if OpenMM is not installed. It is flawless modular design.

## 3. Architectural Lessons Learned from Phase 3

During the intensive stabilization sprints leading up to this audit, several critical but hidden structural vulnerabilities were uncovered and mitigated. These lessons must be preserved as core design principles for future development.

### 3.1 State Synchronization via Dynamic Properties (`@property`)
**Vulnerability**: In the native `Structures` class, the dimensions `n_atoms` and `n_structures` were historically handled as static integer variables that were manually incremented or updated during `add` or `append` operations. This led to severe "ArgumentLengthError" desynchronization bugs when complex trajectories (e.g., merging fragments with varying frames) were concatenated.
**Architectural Fix**: These counters were refactored into dynamic `@property` methods that infer their values directly from the shape of the underlying data arrays (e.g., `self.coordinates.shape`). 
**Rule for 1.0.0**: Native objects must never store static variables for dimensions that can be deterministically inferred from their payload. State must be immutable and self-reporting.

### 3.2 Circular Import Vulnerabilities (The Modular Achilles Heel)
**Vulnerability**: The highly modular directory structure of MolSysMT (`molsysmt/form/X`) creates a dense web of cross-imports. Two major circular import crashes were identified:
1.  **Startup Deadlocks**: `_multiple_conversion_shortcuts` (used for `prmtop` + `inpcrd` conversions) were loaded at the top level of the `_private` module. Because these shortcuts used `@arg_digest`, and `argdigest` itself imports MolSysMT utilities, the package would deadlock on initialization.
2.  **Shadow Recursive Imports**: The pattern `from .to_X import to_X` in form directories caused `TypeError: 'module' object is not callable` when the file name and function name collided in the namespace.
**Architectural Fix**: Strict enforcement of **Lazy Loading**. Cross-module dependencies and shortcut dictionaries are now exclusively imported *inside* the functions that require them (e.g., inside `convert()`), ensuring a clean, millisecond-fast startup tree. Module collisions were resolved by enforcing absolute paths (`from molsysmt.form.Y.to_X import to_X`).

### 3.3 Relational Integrity in Native Topology (The Pandas Engine)
**Vulnerability**: When MolSysMT converts a third-party object (like an OpenMM Topology) to a Native Topology, it must deduce higher-order structures (molecules, entities, components) using graph logic. An early design attempted to propagate `component_index` and `chain_index` from atoms to the `groups` DataFrame as a convenience cache. This created consistency hazards: the groups copy could go stale, and loading from serialized formats (h5msm) that never stored these columns on groups caused `KeyError` at query time.
**Architectural Fix**: `component_index` and `chain_index` are **atom-level attributes only** — they are never stored in `topology.groups`. The canonical schemas are:
- `Atoms_DataFrame`: `['atom_id', 'atom_name', 'atom_type', 'group_index', 'component_index', 'chain_index']`
- `Groups_DataFrame`: `['group_id', 'group_name', 'group_type', 'molecule_index']`

Both DataFrame subclasses enforce this via `__setitem__` guards that raise `AttributeError` immediately if forbidden columns are written. When group-level values are needed (e.g., for serialization or inference), they are derived on demand via pandas `groupby` from the atom-level data using helpers such as `_component_index_per_group(topology)`.
**Rule for 1.0.0**: `component_index` and `chain_index` must **never** appear in `topology.groups`. Any code that writes them there is a bug.

### 3.4 The Danger of Implicit Iterable Validation (`is_a_molecular_system`)
**Vulnerability**: The foundational `is_a_molecular_system` validation logic historically assumed that if an object wasn't a string, it might be an iterable of molecular systems (like a list of files). When pure Python dictionaries were introduced as valid forms (e.g., `molsysmt.MolecularMechanicsDict`), the `else:` block attempted to iterate over the dictionary's keys, treating them as individual molecular systems, which crashed the engine.
**Architectural Fix**: Validation logic has been hardened. Dictionaries are now explicitly handled as atomic configurations before any iterable logic is applied.

### 3.5 Network IO and Self-Copying Bugs (`string:pdb_id`)
**Vulnerability**: When downloading remote files (e.g., pulling a CIF from the PDB using `string:pdb_id`), the extraction pipeline assumed the file always needed to be copied to a new location. If the destination filename was the same as the temporary downloaded file, Python's `shutil.copyfile` threw a `SameFileError`, terminating the conversion prematurely.
**Architectural Fix**: Added strict equality checks (`if copy_if_all or (output_filename != item)`) across all file-based extraction methods. This guarantees safe handling of temporary lifecycle files downloaded via network IO.

### 3.6 Strict Separation of Topology vs. Trajectory Forms
**Vulnerability**: Pure coordinate trajectory formats (like `mdtraj.XTCTrajectoryFile`, `mdtraj.DCDTrajectoryFile`, and `file:h5`) were historically crashing with raw `AttributeError` tracebacks when standard routines attempted to query their `n_atoms` or topological structures.
**Architectural Fix**: These forms have been strictly classified as "pure structural". Instead of crashing, their `get_topological_attributes.py` modules now explicitly raise `NotWithThisFormError("This form does not store topology information directly. Please convert to a topology-enabled form first.")`. This provides a clear, actionable path for the user and maintains strict separation of concerns.

### 3.7 Semantic Purity ("Forma" vs "Formulario")
**Vulnerability**: In Spanish documentation and internal reasoning, the term "form" was sometimes loosely translated to "formulario". This caused semantic confusion, as a "formulario" implies a UI input field, whereas MolSysMT uses "form" to mean the *manifestation* or *nature* of the molecular object.
**Architectural Fix**: A strict semantic guideline has been established: "form" must always be translated to **"forma"** (e.g., "la forma de OpenMM", "la forma de MDTraj"). MolSysMT is fundamentally a "Gestor de Formas Moleculares".

### 3.8 Inference Ordering: Derived Attributes Must Be Written Before Their Consumers
**Vulnerability**: `topology.rebuild_molecules` computed `molecule_name` before `molecule_type`. Because `infer_molecule_names_from_topology` reads `molecule_type` from the molecules DataFrame to decide the naming scheme (e.g. `'peptide 0'`, `'water'`, ion name), the type column was always NaN at the point of name generation. Every molecule fell through to the `'unknown N'` fallback, breaking all `get_molecule_name(..., redefine_names=True)` calls.
**Architectural Fix**: In `rebuild_molecules`, `redefine_types` now runs before `redefine_names`. The underlying principle generalises: **any inference step that reads a derived attribute must be scheduled after the step that writes it**. The `rebuild_*` methods in `Topology` must respect this topological order in all future additions.
**Rule for 1.0.0**: When adding a new `redefine_X` parameter to a `rebuild_*` method, explicitly verify which other `redefine_Y` steps it depends on and enforce the correct execution order.

### 3.9 Force-Field Attributes Belong to `MolecularMechanics`, Not `Topology`
**Vulnerability**: An early version of `build_peptide` wrote AMBER force-field atom types (`atom_ff_type`) directly into `topology.atoms` as an extra column. This violated the separation of concerns between topology (connectivity, names, types in the chemical sense) and molecular mechanics (force-field parameters). It also silently polluted the DataFrame schema, making `topology.atoms` schema-dependent on which code path produced the topology.
**Architectural Fix**: Force-field attributes (`formal_charge`, `partial_charge`, `atom_ff_type`) are stored exclusively in `MolecularMechanics.atoms_ff`, a dedicated `pd.DataFrame` with those columns. The three values are exposed as `@property` accessors on `MolecularMechanics` for convenience. The `Atoms_DataFrame.__setitem__` guard enforces this: writing any of these columns to `topology.atoms` raises `AttributeError` immediately.
**Rule for 1.0.0**: `topology.atoms` columns are: `atom_id`, `atom_name`, `atom_type`, `group_index`, `component_index`, `chain_index`. Any code that attempts to write `atom_ff_type`, `partial_charge`, or `formal_charge` to `topology.atoms` is a bug.

## 4. Architecture of Forms and Files

### 4.1 The Directory Matrix 
**Diagnosis: Incredibly Scalable.**
The decision to separate adapters by "form" (`molsysmt/form/X`) and by operation (`to_Y.py`, `get_structural_attributes.py`) is the major architectural victory of the project. Adding support for a new molecular format requires zero changes to the core; a developer simply creates a new directory and fills in the templates.

### 4.2 File Handler Polymorphism
**Diagnosis: Healed from severe legacy debt.**
Historically, the codebase treated string paths (e.g., `"file.pdb"`) as if they were the file objects themselves, leading to countless `AttributeError: 'str' object has no attribute 'getTopology'` crashes. 
*   **Current State**: The Phase 3 cleanup successfully implemented a "Polymorphic Instantiation" pattern across all IO modules. Handlers now strictly check `isinstance(item, (str, os.PathLike))` and dynamically instantiate the underlying reader (e.g., `openmm.app.PDBFile`) internally. The leakage of the "file abstraction" has been contained.

## 5. System-Level Stability & Future-Proofing

While the topological and mathematical engines are sound, a production-grade 1.0.0 library must guarantee stability at the operating system and interpreter level. The audit revealed three critical blind spots in this domain:

### 5.1 Resource Management and File Descriptor Leaks
**Diagnosis: Active Vulnerability (Medium Priority).**
During the test suite execution, `UnclosedFileWarning` exceptions were silently emitted (e.g., `Closing remaining open file: traj_pentalanine.h5`). 
*   **The Risk**: When MolSysMT converts or extracts data from file-based forms (HDF5, DCD, XTC) via third-party parsers like MDTraj, it dynamically instantiates file handlers. If these handlers are not explicitly closed after data extraction, the file descriptors remain locked in RAM. In high-throughput workflows (e.g., a user iterating over 10,000 trajectories), this will cause the operating system to crash with a `Too many open files` error.
*   **1.0.0 Action Item**: Enforce strict Context Manager patterns (`with ... as file:`) or explicit `.close()` calls in `finally` blocks within all `get_*.py` and `to_*.py` adapters that open file streams.

### 5.2 Thread Safety in the JIT Compiler
**Diagnosis: Architectural Limitation (Requires Documentation).**
The custom `lazy_njit` engine in `molsysmt/_private/jit.py` is brilliant for preventing recursive compilation, but it relies on global state variables (`_COMPILING = set()`, `_WRAPPER_COMPILED = {}`) to track compilation progress.
*   **The Risk**: If a user attempts to run MolSysMT inside a highly parallel, multi-threaded environment (e.g., using `ThreadPoolExecutor` or Dask) *before* the kernels are compiled, multiple threads may simultaneously attempt to mutate this global state. This can lead to race conditions, corrupted Numba dispatches, or deadlocks.
*   **1.0.0 Action Item**: Either introduce `threading.Lock` mechanisms within `lazy_njit` to make the JIT thread-safe, or explicitly mandate in the documentation that users MUST run `molsysmt.warmup_numba()` on the main thread before spawning parallel workers.

### 5.3 Developer Experience (DX): Static Typing vs. Runtime Digestion
**Diagnosis: DX Friction Point.**
MolSysMT possesses a world-class *runtime* validation system (`@arg_digest`), but modern Python development heavily relies on *static* analysis (Mypy, Pyright, VSCode IntelliSense).
*   **The Risk**: Because `@arg_digest` heavily decorates the public API, IDEs often struggle to infer the true function signatures or return types. A user typing `msm.convert(` might not get helpful type hints, reducing the discoverability of the API.
*   **1.0.0 Action Item**: Audit the deployment of type hints (e.g., `.pyi` stub files or `typing` module annotations) for the primary public API surface (`basic/`). Bridging the gap between dynamic digestion and static inference is crucial for enterprise adoption.

## 6. Scalability, Memory & Documentation

Beyond functional correctness, a 1.0.0 scientific library is judged by its ability to handle massive datasets and by the quality of its user-facing documentation. The audit identified the following critical areas:

### 6.1 "Out-of-Core" Memory Models vs. In-Memory Loading
**Diagnosis: Resolved for 1.0.0.**
- **Status**: [COMPLETED] The implementation of `molsysmt.basic.Iterator` and the internal Chunked Engine now provide a native "Out-of-Core" model.
- **Result**: The library can process massive trajectories without exceeding available RAM via chunked iterators over native and supported formats.


### 6.2 The Maturity of Native File Handlers
**Diagnosis: Incomplete Native Ecosystem.**
MolSysMT correctly delegates heavy lifting to OpenMM and MDTraj. However, it also includes native file handlers (e.g., `molsysmt.H5MSMFileHandler`, `pdb_file_handler.py`).
*   **The Risk**: A quick scan reveals that several native file handlers still contain `raise NotImplementedError` in internal methods (e.g., in `gro_file_handler.py`, `simulation.py`). 
*   **1.0.0 Action Item**: Any native handler exposed to the public API must be fully functional. If a handler is experimental or incomplete, it should be marked with a DeprecationWarning/UserWarning or removed from the Tier 1/Tier 2 support list until fully baked.

### 6.3 Decorators and Sphinx Documentation Generation
**Diagnosis: Potential DX (Developer Experience) Risk.**
The public API relies heavily on stacked decorators (`@signal(tags=['api'])`, `@arg_digest()`).
*   **The Risk**: Python decorators, if not carefully constructed using `functools.wraps`, can obliterate the original function signatures and docstrings. When tools like Sphinx or IDEs try to read `molsysmt.convert`, they might display generic signatures like `(*args, **kwargs)` instead of the actual parameters, severely degrading the documentation quality.
*   **1.0.0 Action Item**: Perform a dry-run build of the Sphinx documentation. Ensure that `argdigest` and `smonitor` decorators perfectly preserve the `__signature__`, `__doc__`, and `__annotations__` of the wrapped public functions.

## 7. Software Engineering & Code Smells

A deep scan for standard software engineering anti-patterns revealed the following:

### 7.1 "Bare Excepts" [COMPLETED]
**Diagnosis: Cleaned and Hardened.**
All instances of raw `except:` clauses have been refactored to `except Exception as e:` or specific exceptions.
- **Result**: Improved security by preventing the masking of system signals (`KeyboardInterrupt`) and easier debugging.

### 7.2 Error Handling Consistency (`smonitor` vs Native)
**Diagnosis: 95% Unified.**
The `smonitor` system is heavily utilized, providing excellent, context-aware exceptions (`ArgumentError`, `NotSupportedFormError`). 
*   However, there remain approximately **59 isolated instances** of native `raise ValueError` inside deep core logic (e.g., Native topology merging, PBC bounding box calculations).
*   **1.0.0 Action Item**: Sweep the codebase to wrap these remaining native exceptions into `smonitor` exceptions. No raw Python errors should leak to the end-user without the MolSysMT documentation context attached.

### 7.3 Declared Technical Debt (`TODO` / `FIXME`)
**Diagnosis: Exceptionally Clean.**
There are only **3 explicit `TODO` markers** in the entire repository (located in the MMTF to MDTraj converter and bondgraph topology). This proves that technical debt is not being hidden in comments; it is either being actively resolved or architecturally acknowledged.

## 8. Final Verdict for 1.0.0

Is MolSysMT mathematically robust? **Yes.**
Is the architecture scalable? **Absolutely.**

MolSysMT is a marvel of bioinformatics engineering. The concept of a "Molecular Form Manager" (Gestor de Formas Moleculares) has been implemented brilliantly. The topological inference engines, the PBC operations, and the polymorphic ecosystem integrations are world-class.

To declare version 1.0.0 "Rock Solid", the final programming tasks should be strictly limited to:
1.  **Refactoring the Bare Excepts** (`except:` -> `except Exception:`).
2.  **Sweeping residual `ValueError` exceptions** into the SMonitor catalog.
3.  **Resolving the final ~10 test failures** (which are mostly edge-cases related to OpenMM PDB iterations and pure-trajectory atomic inferences).

Once these are complete, MolSysMT will stand on equal footing in terms of stability and code maturity with ecosystem giants like NumPy and MDAnalysis.
