# MolSysMT 1.0.0 Maturity Audit & Action Plan

## Executive Summary: Where do we stand?
To use a construction metaphor: **MolSysMT has the foundations of a skyscraper, but it still has scaffolding on the windows.** The architectural design is world-class, but the implementation still carries "experimental scars" that must be healed before a 1.0.0 release.

### Maturity Snapshot
- **Architecture & Design: 100%** (Lazy registry, polymorphic handlers, and clean hierarchies).
- **Ecosystem Integration: 100%** (Full parity verified for Native, MDTraj, OpenMM, MDAnalysis, and ParmEd).
- **Robustness & Hardening: 95%** (Contract tests cover 90% of structural/topological API).

**The Verdict:** The ecosystem integration phase is officially COMPLETE. MolSysMT is ready for final documentation and performance tuning. The foundations are indestructible.

**Estimated Effort:** 3 to 5 months of dedicated work (team of 2-3) focused exclusively on stability.
**Primary Risk:** "Feature Creep"—the temptation to add support for new formats or libraries before the core Tier 1 forms are fully hardened.


## Context and Purpose
This document provides a critical, in-depth audit of MolSysMT's current state as it approaches the `1.0.0` milestone. This is not just another minor release; **`1.0.0` represents a shift from "experimental utility" to "production-grade scientific infrastructure."**

This audit evaluates MolSysMT both as a standalone library and as the orchestrator of the UIBCDF ecosystem (`smonitor`, `depdigest`, `argdigest`, `pyunitwizard`). It is written to be explicit and actionable for developers joining the stabilization effort.

---

## 1. The Flexibility Paradox (Public API Stability)
MolSysMT's greatest strength is its ability to accept almost any object as a `molecular_system` (files, trajectories, topologies). However, this extreme flexibility creates internal complexity (e.g., the dense logic in `molsysmt.basic.get` and `convert`).

**The Risk:** A minor adjustment to support a new form can silently break existing, well-established forms.
**The 1.0.0 Mandate: Contract Testing**
- The public API (`molsysmt.basic.*`) must be frozen.
- We must implement **Contract Tests**. It is not enough to test if `get()` runs without crashing; tests must assert that the exact schema of the output (data types, list nesting, physical units) remains mathematically identical across versions.

## 2. The Glass Ceiling of Code Coverage
The current `implementation_plan.md` sets a coverage goal of >= 75%. For a core infrastructural library, this is insufficient.

**The Risk:** Subtle bugs in topology handling (e.g., a misplaced bond, an off-by-one atom index) will not be caught by "smoke tests."
**The 1.0.0 Mandate: 90% Core Coverage**
- Core modules (`molsysmt/basic`, `molsysmt/native`, `molsysmt/element`, `molsysmt/form/native`) must reach **>= 90% coverage**.
- Integration modules (`thirds` and obscure file parsers) can remain at lower coverage, but the mathematical and structural core must be heavily tested.

## 3. The Labyrinth of Forms (Adapter Maintenance)
Maintaining dozens of adapters for third-party libraries (MDTraj, OpenMM, ParmEd) is a heavy burden. When an external library updates, MolSysMT risks breaking.

**The Risk:** Claiming "full support" for a form that is only lightly tested damages user trust.
**The 1.0.0 Mandate: Formal "Support Tiers"**
We must classify forms into explicit support tiers in the documentation:
- **Tier 1 (First-Class):** Guaranteed support, fully tested in CI (e.g., `molsysmt.MolSys`, `openmm.Topology`, `mdtraj.Trajectory`, standard PDBs).
- **Tier 2 (Community/Best-Effort):** Supported but tests may not cover all edge cases (e.g., niche file formats). Users are explicitly warned about the tier level.

## 4. Total Ecosystem Integration (The "AI-Ready" Goal)
MolSysMT is the flagship consumer of the UIBCDF infrastructure. It must lead by example.

**The Risk:** If MolSysMT bypasses the underlying infrastructure (e.g., raising raw Python exceptions instead of using SMonitor), the whole "Self-Healing/Autonomous" vision falls apart.
**The 1.0.0 Mandate: Zero Ad-Hoc Exceptions**
- **SMonitor:** *Every* warning and error raised within the core must be migrated to the SMonitor `CATALOG` (`_private/smonitor/catalog.py`). No more `raise ValueError("Invalid format")`. It must be an actionable, catalogued event with a `code` and a `hint`.
- **ArgDigest:** Ensure all public functions use `@arg_digest` to normalize inputs (especially `selection` and `syntax`).
- **DepDigest:** Ensure no heavy dependency (e.g., `mdanalysis`) is imported at the top level of any module.
- **PyUnitWizard:** Ensure all functions that return physical quantities consistently return PyUnitWizard objects, governed by a global ecosystem configuration.

## 5. The Hidden Startup Cost
Through `depdigest` and lazy loading, MolSysMT imports very quickly. However, the *first* execution of a function like `convert` incurs a heavy penalty (discovering forms via `LazyRegistry` and warming up Numba JIT compilers).

**The Risk:** Users perceive the library as "slow" during short, interactive notebook sessions.
**The 1.0.0 Mandate: Controlled Warmup**
- Expose and document a clear `molsysmt.warmup()` function for users who want to pay the compilation cost upfront.
- Audit the `LazyRegistry` in `molsysmt/form/__init__.py` to ensure directory scanning does not thrash network file systems (NFS/HPC) unnecessarily.

---


## 6. Persistence & The "Native" Source of Truth
MolSysMT relies on its native format (`.h5msm`) and its internal data model (`molsysmt.native`). 1.0 implies long-term stability for stored data.

**The Risk:** Files saved with 1.0 becoming unreadable in 1.1, or internal refactors breaking third-party adapters.
**The 1.0.0 Mandate: Schema Versioning & Native Lock**
- **H5MSM Stability:** Define a formal versioning for the H5MSM schema. Ensure forward/backward compatibility or provide clear migration tools.
- **Internal Schema Freeze:** The structure of the `molsysmt.native` objects must be frozen and documented as an internal contract.

## 7. Documentation as Code (Notebook CI)
Scientific users rely on Jupyter Notebooks as their primary source of truth for "how to use the library."

**The Risk:** Outdated examples in `docs/` or `examples/` creating a perception of a "broken" library.
**The 1.0.0 Mandate: Automated Notebook Execution**
- All documentation notebooks must be integrated into the CI pipeline. A change in the API that breaks a notebook must be treated as a CI failure.

## 8. Selection Language Homogeneity
The selection syntax (e.g., `selection="atom_name=="CA""`) is the primary user interface.

**The Risk:** Inconsistent behavior of the same selection string across different Tier 1 forms.
**The 1.0.0 Mandate: Cross-Form Selection Testing**
- Implement a comprehensive test suite that ensures identical selection strings return identical indices across all Tier 1 forms.


## 🛣️ Roadmap to 1.0.0: The Stabilization Path

This roadmap breaks down the stabilization effort into four focused phases. Each phase must be completed and verified before moving to the next.

### 🏁 Phase 1: Infrastructure Cleanup & API Alignment (COMPLETED)
*Focus: Bringing MolSysMT up to the ecosystem standards.*

- [x] **SMonitor Migration**: Audit all `raise` statements in `molsysmt/basic` and `molsysmt/form` and replace them with `smonitor` catalog emissions. (Including `caller` enforcement).
- [x] **ArgDigest Enforcement**: Ensure *every* function in `molsysmt.basic`, `structure`, `topology`, and `molecular_dynamics` is wrapped with `@arg_digest` and `@signal`.
- [x] **Dependency Audit**: Universal Lazy Loading implemented across all forms. `import molsysmt` is now fast.
- [x] **Unit Standardization**: Input normalization via ArgDigest/PyUnitWizard and output standardization in `basic.get`.
- [x] **API Surface Documentation**: Public functions are instrumented; internal cross-form imports are explicit.

### 🛡️ Phase 2: Core Hardening & Contract Locking (IN PROGRESS)
*Focus: Creating a \"Black Box\" of reliability for Tier 1 forms.*

- [x] **Tier 1 Contract Tests**: Implement tests that assert output schemas (types, shapes, units) for `get` across all Tier 1 forms. (Identity verified for Native, MDTraj, and OpenMM).
- [ ] **Internal Schema Freeze**: Document and freeze the `molsysmt.native` data model as an immutable internal contract.
- [ ] **H5MSM Versioning**: Add version metadata to the `.h5msm` format and implement a forward-compatibility check.
- [x] **Selection Homogeneity**: Implement the \"Cross-Form Selection\" test suite to ensure `selection` strings behave identically across Tier 1 forms.

### 🧪 Phase 3: Quality Assurance & Documentation CI (Month 3)
*Focus: Reaching the 90% coverage threshold and validating docs.*

- [ ] **Coverage Push (90%)**: Target the dense decision logic in `basic.get` and `_piped_molecular_system`.
- [ ] **Notebook CI Integration**: Configure the CI to execute all tutorials/examples; failures in notebooks must block PR merges.
- [ ] **Tiered Forms Table**: Publish the Support Tiers table in the user documentation.
- [ ] **Error Code Registry**: Publish the full list of SMonitor codes and hints in the developer documentation.

### 🚀 Phase 4: Optimization & Final Release (Month 4)
*Focus: Performance tuning and ecosystem finality.*

- [ ] **Warmup Ergonomics**: Implement `molsysmt.warmup()` to pre-compile Numba kernels and scan the form registry.
- [ ] **Registry Optimization**: Audit `LazyRegistry` scanning to minimize I/O overhead on network file systems (HPC).
- [ ] **Ecosystem Validation**: Run the "Collective Finality Criterion" (automatic error flow from `pyunitwizard` to `smonitor` via `argdigest`).
- [ ] **Final Go/No-Go**: Final audit against the `Collective V1 Checklist`.

MolSysMT will be considered `1.0.0` ready when:
1. Core coverage is **>= 90%**.
2. **Zero raw exceptions** are raised in the public API (all go through SMonitor).
3. All **Tier 1 Contract Tests** pass consistently.
4. **Notebook CI** is green for the entire documentation set.
