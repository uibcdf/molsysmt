# Numba Migration Inventory — Historical Evidence of a Closed Migration

> **The migration described here is complete.** Numba was the temporary
> scientific oracle for the Rust port, and it no longer ships. Segment D of the
> 1.0 execution plan removed every CPU JIT kernel, every CUDA JIT kernel, the
> dispatch layer, the `warmup()` API, and the dependency itself. Segment B
> preserved the final two-backend comparison in
> [`release_1_0_final_numba_oracle_artifact.md`](release_1_0_final_numba_oracle_artifact.md).
>
> This document is retained for provenance: it records what the temporary surface
> was and how it was frozen. It does **not** describe a live migration, and the
> counts in the 2026-07-26 baseline table below are a historical snapshot, not the
> current state.
>
> The ratchet script still runs, and its job is now the opposite one — proving the
> surface stays at zero rather than shrinking towards it. A current run reports 0
> direct imports, 0 CPU JIT sites, 0 CUDA JIT sites, and 0 direct consumers; the
> only remaining categories are development tools, one build file, and
> documentation that mentions the migration by name, including this file.
>
> For current execution behaviour see
> [`performance_and_jit.md`](performance_and_jit.md); for how the Rust kernels are
> optimized see
> [`rust_kernel_optimization_guide.md`](rust_kernel_optimization_guide.md).

## Original purpose

Numba was a temporary scientific migration oracle, not a second implementation
that MolSysMT 1.0 would maintain. The inventory generated by
`devtools/scripts/audit_numba_surface.py` froze that temporary surface while
the Rust implementation was productized.

The machine-readable baseline is
`devtools/data/numba_surface_baseline.json`. It is generated from source; it is
not a hand-maintained claim and must not be edited directly.

## Commands

Checking the monotonic migration ratchet:

```bash
python devtools/scripts/audit_numba_surface.py
```

Inspecting the current generated payload without changing the baseline:

```bash
python devtools/scripts/audit_numba_surface.py --json
```

Regenerating the baseline after reviewing an intentional reduction or
classification change:

```bash
python devtools/scripts/audit_numba_surface.py --write-baseline
```

The check runs in the smoke CI workflow. A new guarded identity fails CI. That
guard outlives the migration: with the surface at zero, any reintroduced `numba`
import or JIT decorator is rejected.

## Stable Guarded Identities

The ratchet uses AST-derived identities rather than counts or line numbers:

- direct `numba` and `llvmlite` imports: `path::imported module`;
- CPU and CUDA JIT-decorated functions, kept as separate categories:
  `path::qualified callable::decorator`;
- CUDA-coupled runtime modules: repository-relative path;
- consumers importing a JIT-coupled `molsysmt.lib` module:
  `path::imported module`.

Moving a function within a file does not create false debt. Replacing one
kernel with another while keeping the total count unchanged is detected.
Removing a recorded identity is allowed and reported; adding one is rejected.

## Broader Removal Surfaces

The generated payload also records file-level surfaces that must reach zero or
an explicitly approved archived state during the Rust-only cut:

- runtime references and control/configuration files;
- package and conda dependencies;
- tests and development tools;
- CI/build files;
- the Rust migration experiment;
- web documentation and the active developer guide.

These categories were informational during the oracle phase because parity
tests and migration documentation still had to mention Numba. They are
deliberately file-granular rather than line-granular to avoid a noisy baseline.
The zero-Numba gate required the active categories to be empty and permitted
historical mentions only under the developer-guide archive and the dated final
migration record. That gate passed as stage D5.

## Scope and Limitations

The AST inventory recognizes ordinary Python imports and decorators. The
file-level runtime scan provides a second safety net for indirect strings,
configuration, diagnostics, and helper references that are not imports.
Generated notebook outputs are ignored; only notebook cell sources are
inspected. Showcase notebooks are excluded because their stored visualization
payloads are not release instructions.

The inventory does not prove Rust parity or scientific correctness. The
[CPU Numba-to-Rust Oracle Map](numba_cpu_oracle_map.md) added the
kernel-to-Rust-consumer-evidence classification, and B4/B5 preserved the final
two-backend comparison. The precondition recorded here — that Numba deletion was
blocked until production Rust packaging passed on the declared platform and
Python matrix — was satisfied by Segment C before Segment D deleted it.
