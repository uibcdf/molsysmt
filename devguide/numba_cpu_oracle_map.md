# CPU Numba-to-Rust Oracle Map

## Purpose

The CPU oracle map proves that every CPU JIT callable frozen by the active
Numba inventory has an explicit Rust migration disposition. It prevents a
Numba-only capability from disappearing unnoticed when the temporary oracle is
retired.

The machine-readable artifact is
`devtools/data/numba_cpu_oracle_map.json`. It is generated by
`devtools/scripts/audit_numba_oracle_map.py` and must not be edited directly.

This is a transitive map:

1. every CPU JIT callable belongs to exactly one scientific or infrastructure
   family;
2. every callable has a Rust target or an explicit absorbed-helper target;
3. every family names its high-level MolSysMT consumers;
4. every family names two-backend parity tests;
5. every family names scientific or property evidence that does not rely only
   on agreement with the Numba result.

The map is not itself proof of numerical parity. The executable tests and the
dated final two-backend campaign provide that evidence.

## Commands

Checking the committed artifact against the live Numba and Rust surfaces:

```bash
python devtools/scripts/audit_numba_oracle_map.py
```

Inspecting the generated map:

```bash
python devtools/scripts/audit_numba_oracle_map.py --json
```

Regenerating the artifact after an intentional reviewed reduction:

```bash
python devtools/scripts/audit_numba_oracle_map.py --write-manifest
```

Both the active-Numba inventory and this oracle-map check run in smoke CI. A
new CPU kernel, an unclassified helper, a missing evidence path, or a stale
artifact fails the check.

## Mapping Kinds

| Kind | Meaning |
| --- | --- |
| `direct` | A private Rust backend dispatcher has the same callable name and routes to the Rust extension. |
| `alias` | The capability is direct, but the obsolete Numba helper name differs from the Rust dispatcher name. |
| `absorbed` | The Numba callable is an implementation helper incorporated into a larger Rust algorithm or a private Rust helper; no separate Python export is required. |

An absorbed mapping is not permission to omit behavior. It must name the Rust
operation that owns the behavior, and the owning family must pass parity and
independent scientific or property checks. Creating one-to-one Python exports
for internal vector operations, minimum-image helpers, or neighbor-list
subroutines would make the replacement architecture worse without adding
scientific capability.

## Current Result

The 2026-07-26 artifact maps all 108 inventoried CPU JIT callables across 15
families:

| Mapping | Count |
| --- | ---: |
| direct Rust dispatcher | 87 |
| renamed alias | 1 |
| absorbed helper | 20 |

The complete Rust test surface passes with 264 tests and 3 documented upstream
minimum-image skips. The selected independent scientific-truth surface passes
82 tests covering PBC, structure, topology, external geometry oracles, and a
curated trajectory.

No missing CPU Rust capability is demonstrated by this map. New Rust kernels
must not be added merely to reproduce the old helper layout. A kernel becomes
necessary only if the divergence review or the final parity campaign
demonstrates behavior that the mapped Rust route does not provide.

## Evidence Interpretation

`parity_tests` compare the temporary Numba oracle and Rust route directly.
They establish migration equivalence within the tolerance recorded by the
test, but agreement between two implementations is not sufficient scientific
truth by itself.

`independent_evidence` therefore points to at least one of:

- an external scientific implementation or curated reference;
- an independently calculated property or brute-force ground truth;
- a scientific invariant;
- Rust unit/property tests for small internal helpers whose behavior is
  defined mathematically rather than by Numba.

The last category is intentionally narrower than external validation. It is
appropriate for operations such as vector algebra, integer series
transformations, and topology primitives, but it does not replace
system-level scientific validation.

## Permanent Rust Architecture

The final Rust source belongs to the MolSysMT repository but should not be
mixed into the Python module tree. Segment C will move the production crate out
of `experiments/` into a dedicated Rust workspace. The compiled extension will
be installed as a private module inside the `molsysmt` package, provisionally
`molsysmt._rust` or `molsysmt._native`.

Public scientific calls remain under their existing modules, for example
`molsysmt.structure.get_distances`. Users must not depend on a parallel public
Rust API. This separation permits `molsysmt/lib` to be removed after direct
Rust routing, packaging, parity, and installed-wheel evidence are complete.

## Remaining Gates

This artifact closes only the CPU capability-classification stage. It does not
authorize deleting Numba. The remaining required work is:

1. record every intentional numerical or behavioral divergence and its
   tolerance;
2. run and preserve the final reproducible two-backend campaign;
3. productize and test the private Rust extension on the supported platforms;
4. route production consumers directly through Rust;
5. audit the separate Numba-CUDA surface;
6. remove CPU and CUDA Numba code, dependencies, controls, diagnostics, and
   documentation;
7. pass the executable zero-Numba gate in a clean installed environment.
