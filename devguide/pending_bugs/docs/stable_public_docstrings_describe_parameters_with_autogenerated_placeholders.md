# Bug: `Argument to_form.` is not a description of `to_form`

**Reported:** 2026-08-19, during an external audit, while reading `msm.convert` and
`msm.get` as a new user would.
**Status:** open. The docstring gate passes on every one of these, by design.

## What

Eighteen of the fifty documented stable symbols in the root namespace describe at least
one parameter with the autogenerated placeholder `Argument <name>.`, 49 parameters in
total. They include the most-used arguments in the library:

```
molsysmt.convert                       to_form, strict, return_report
molsysmt.get                           mask, get_missing_bonds, output_type, chemical_state
molsysmt.select                        mask, to_syntax, chemical_state
molsysmt.merge                         molecular_systems, selections, keep_ids, to_form
molsysmt.compare                       molecular_system_2, rule, output_type, attribute_type, include_none
molsysmt.add                           to_molecular_system, from_molecular_system, keep_ids, in_place, attribute_policy
```

As rendered to a user:

```python
>>> help(msm.convert)
    to_form : object, default=None
        Argument to_form.
```

`to_form` is the argument that selects one of 89 destinations and decides what the
function returns. Its documentation restates its name.

The pattern is not confined to the stable surface. Across the package:

```bash
$ grep -rn 'Argument [a-z_]*\.$' --include='*.py' molsysmt | wc -l
9976
$ grep -rn 'Resulting object in object form' --include='*.py' molsysmt | wc -l
8810
```

`msm.build.solvate` documents 9 of its 12 parameters this way, including `box_shape`,
`clearance`, `ionic_strength` and `engine` — the four a caller must actually choose.

## How

The text is generated, and the gate that checks docstrings checks structure rather than
content. `devtools/scripts/validate_docstrings.py` verifies that every signature
parameter appears in the `Parameters` section and that documented defaults match the
signature. A placeholder satisfies both. So the generator filled the sections, the gate
confirmed the sections were filled, and nothing asked whether the filling said anything.

The type field degrades the same way: `to_form : object` where the value is a form name
string, `mask : object`, `output_type : object`. `AGENTS.md` requires types in lowercase
and defaults in the description; a generated `object` meets the letter of that.

The result is uneven inside single docstrings rather than uniformly poor. `msm.get`
carries a genuinely good extended description — nine paragraphs of `Notes` on chemical
states, mixed element levels and derived attributes — above four parameters described as
`Argument mask.` The care went into the prose and stopped at the parameter table.

## Why

**This is the 1.x contract surface.** These 18 symbols are `stable` in
`devtools/data/public_api_stability.json`. The project promises their signatures for the
whole 1.x line and does not say what four of `get`'s arguments do.

**It is what a reader from the paper meets first.** `help()`, the rendered API reference,
and an IDE tooltip all show the parameter table before anything else. A table that
restates names reads as generated documentation, and it discredits the hand-written
material next to it — which is, in this repository, substantial and good.

**The gate's silence is the durable part.** Until content is checked, the next generated
surface will pass too. Any effort spent rewriting these 49 entries is undone by the next
scaffold unless the criterion is encoded.

Severity is `medium`: nothing is wrong, something is missing, and the missing thing sits
on the contractual surface at the moment it is being frozen.

## What is measured and what is assumed

Measured, with the script whose output is quoted above: 50 stable symbols carry a
docstring, 18 carry placeholders, 49 parameters are affected; the two repository-wide
counts; the 9 of 12 in `solvate`.

The 123 stable symbols do not all resolve to an object with a docstring — exception
classes and namespace modules account for the rest — so the denominator is 50, not 123.

Assumed: nothing. The measurement is a regular expression over `inspect.getdoc`, and the
pattern `^\s*Argument (\w+)\.$` has no plausible legitimate use.

## What was refuted

*The docstring validator is not run.* It is: `test_validate_docstrings.py` is in
`devtools/tests/` and the gate passes. It checks presence and default fidelity, which is
what it was written to check.

*The placeholders are confined to the generated form layer.* They are not. The form layer
carries the bulk of the 9,976 occurrences, but 18 root-namespace public functions carry
them too, and those are hand-maintained files.

## Scope and exclusions

Covers the 49 placeholder parameters on the stable root surface, and the gate criterion
that lets them pass.

Excludes the ~10,000 occurrences inside `molsysmt/form/`, which are a different problem
of a different size and are [#189](https://github.com/uibcdf/molsysmt/issues/189).
Excludes `Returns` sections, which have their own generated phrasing
(*"Resulting object in object form"*) and are worth a separate pass once the criterion
exists. Excludes the experimental surface, `build.solvate` included: it is quoted here as
evidence of reach, and fixing it is not required to close this.

## Acceptance criteria

1. No `stable` symbol documents a parameter as `Argument <name>.`, and none types a
   parameter `object` where a concrete type or a union applies.
2. `validate_docstrings.py` rejects a parameter description that restates the parameter
   name and one that is empty, so the next generated surface cannot reintroduce them.
   This is the `guard`.
3. `AGENTS.md` states the criterion in the docstring section, so it is a rule and not
   only a check.
