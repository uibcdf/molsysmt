Documentation Agents Guide#

This guide is for agents and contributors editing documentation under docs/ and other markdown-based guides in this tree. It refines the global rules in the repository root AGENTS.md.

Language, style, and tone#

  • All documentation must be written in English.

  • Follow the writing style described in docs/README.md and docs/dev/developer_guide.md: short, direct sentences, user-focused (“you”), and consistent terminology with the API.

  • Summaries and headings for functions or tutorials should use gerund phrasing when matching docstrings (for example, “Getting box lengths and angles.”).

  • For scientific quantities, always mention units explicitly (nm, ps, radians, elementary charge).

Markup and MyST/Sphinx usage#

  • Pages under docs/content and docs/dev use Markdown/MyST with Sphinx directives.

  • Use MyST admonition syntax for blocks such as:

    • :::{admonition} API documentation ... :::

    • :::{seealso} ... :::

    • :::{versionadded} 1.0.0 :::

  • Do not introduce reST-only admonition syntax inside notebooks; follow the patterns in docs/dev/developer_guide.md.

  • Use {func} and related roles for cross-references to API objects, and keep anchors stable.

  • Prefer labeled sections plus {ref} for internal links between documentation pages instead of hard-coding file paths; see docs/content/developer/documentation/web/references.md for detailed patterns.

Structure and file layout#

  • Respect the existing structure under:

    • docs/content/ for user guides, showcases, and conceptual docs.

    • docs/dev/ for developer and contributor documentation.

    • docs/api/ and docs/old_api/ for autogenerated API references.

  • Do not modify or overwrite autogenerated outputs in _build/, _gettext/, _locale/, or other generated directories.

  • Template and theme assets in _templates/ and _static/ should only be changed when adjusting global look-and-feel, and changes should be minimal and coordinated with conf.py.

Consistency with code and tests#

  • Keep documentation examples in sync with actual APIs and tested behavior:

    • Function and class names must match the code exactly, including capitalization and module paths.

    • Examples that involve units should use the same units and shapes as enforced in tests (for example, coordinates in nm, box as (n_structures, 3, 3)).

  • Avoid duplicating long examples already present in docstrings; instead, link to API docs and focus on narrative usage and context.

Notebooks and tutorials#

  • For tutorial notebooks (*.ipynb), follow the structure and conventions described in docs/dev/developer_guide.md: title, italic gerund summary, introduction, API documentation admonition, versionadded block, narrated examples, and seealso section.

  • Keep notebooks executable and lightweight; avoid heavy computations, long trajectories, or network access.

  • When updating notebooks, ensure they still run cleanly under the CI notebook execution scripts (for example, execute_notebooks.py).

Safety and maintenance#

  • Do not introduce documentation that contradicts dev_guide.md or coding/coding_guide.md; if behavior changes, update those guides as well.

  • Keep examples minimal but complete enough to be copied and run by users.

  • When reorganizing sections or navigation (for example, index.ipynb or content/*/index.md), update toctrees and verify that Sphinx builds successfully with make html from the docs/ directory.
