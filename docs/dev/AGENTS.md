# Docs/Dev Agents Guide

This guide is for agents editing developer documentation and tutorials under
`docs/dev` and related folders. It refines the global rules in `docs/AGENTS.md`
for developer-facing content.

## Language and audience

- All content must be written in English.
- These documents target developers and contributors to MolSysMT; assume familiarity with Python and basic molecular simulation concepts.
- Keep tone clear and instructional; prefer concise explanations over informal commentary.

## Tutorials and dev notes

- Follow the structure and recommendations in `docs/dev/devnotes_tutorial.md` and `docs/dev/developer_guide.md` when editing or creating tutorials:
  - Anchor + title.
  - One-line italic summary in gerund form.
  - Short introduction.
  - `API documentation` admonition using MyST syntax.
  - `versionadded` admonition.
  - Narrated examples with varied phrasing.
  - Closing `seealso` block with links to related tutorials.
- All admonitions must use MyST syntax (`:::{admonition}`, `:::{seealso}`, `:::{versionadded}`, etc.), not reST.
- Tutorials should complement, not duplicate, examples already present in docstrings; emphasize workflows and combined usage.

## Docstrings and internal guides

- Keep guidance about docstrings aligned with the main developer and coding guides:
  - NumPy-style layout, gerund summaries, explicit units, and single `Returns` section.
  - Avoid contradicting `dev_guide.md`, `coding/coding_guide.md`, or the docstring notes in `docs/dev/developer_guide.md`.
- When updating internal documentation about style or conventions, ensure it remains consistent with actual code examples and AGENTS files.

## References and cross-links

- Link APIs using `{func}` roles where possible, without adding extra parentheses unless referring to a call form explicitly.
- Use labeled sections plus `{ref}` for internal links between documentation pages instead of hard-coding file paths; follow the patterns in `docs/content/developer/documentation/web/references.md`.
- Keep anchors, section titles, and references consistent so that cross-links remain stable.
- When adding new sections, choose clear, descriptive headings and ensure they appear correctly in any toctrees that reference them.

## Generated content and build artifacts

- Do not modify `_build`, `_gettext`, `_locale`, or any other autogenerated outputs under `docs/`.
- Developer guides and notes in `docs/dev` should describe how to run Sphinx builds (for example, `make html`) but should not alter build output directly.

## Safety and evolution

- When changing conventions documented here (for example, tutorial structure, naming, or admonition usage), consider their impact on existing notebooks and docs and update them consistently.
- Keep examples and snippets minimal but accurate; they should be easy to copy and run in a development environment.
